# Design

## Context

Мотивация в proposal.md. Что есть сейчас:

- `daylog.py` (один файл, только stdlib). `run` раз в минуту снимает экраны и пишет строку в `captures.jsonl`; пачками по 5 минут `summarize` описывает кадры через `claude -p`, пишет `minutes.jsonl` и удаляет кадры; `report` склеивает минуты в интервалы и пишет `report.md`.
- Данные: `$DAYLOG_DIR` (по умолчанию `~/.local/share/daylog`), по каталогу на день `YYYY-MM-DD/`:
  - `captures.jsonl`: `{"t": "09:28", "app": "Warp", "frames": ["0928-d1.jpg", "0928-d2.jpg"]}`. Одна строка = одна минута за компьютером.
  - `minutes.jsonl`: `{"t": "14:41", "app": "Warp", "activity": "…"}`. Строки могут идти не по порядку времени; `activity` бывает `(нет описания)`.
  - `report.md`, `summarize.log`, `summarize.lock`, `frames/`.
- Минута из `captures.jsonl`, которой нет в `minutes.jsonl`, ещё не описана.
- Сборщик не снимает минуту, если ввода не было дольше 3 минут (`IDLE_SEC`): долгий уход от компьютера виден как пропуск, а не как время в приложении. Но и минута с вводом может быть не о работе, поэтому по приложению нельзя понять, работал ли человек.
- Сборщик запускают руками в отдельной вкладке терминала: разрешение Screen Recording выдано терминалу. macOS привязывает это разрешение к приложению, от имени которого порождён процесс, поэтому сборщику, запущенному из daylog.app, нужно разрешение на daylog.app.
- Окружение: macOS, cargo 1.98, tauri-cli 2.2.2, node 24, pnpm. Репозиторий не под git.

## Goals / Non-Goals

**Goals:**

- Приложение читает те же файлы, что пишет `daylog.py`, и не дублирует его логику сбора и вызова LLM.
- Открытый сегодняшний день обновляется сам, пока сборщик пишет минуты.
- Запись включается и выключается кнопкой в приложении; терминал для обычной работы не нужен.
- Изменения в `daylog.py` минимальные и не ломают запуск из терминала.
- Итоги дня отвечают на вопрос, сколько было работы, а не в каких приложениях.

**Non-Goals:**

- Перенос сбора кадров в Rust: сборщиком остаётся `daylog.py run`.
- Иконка в строке меню, запуск при входе в систему.
- Запись файлов дней со стороны приложения (кроме перенаправления вывода сборщика в `collector.log`).
- Кросс-платформенность: только macOS.
- Подпись, нотаризация, автообновление. Приложение собирается и запускается локально.

## Decisions

### Расположение и стек

`app/` в корне репозитория: `app/src` (React 18 + TypeScript + Vite), `app/src-tauri` (Rust, Tauri 2). Пакетный менеджер pnpm. Без UI-библиотек и роутера, стили обычным CSS с переменными, тема по `prefers-color-scheme`. Состояние в React (`useState`/`useReducer`), без стора.

Альтернатива — локальный веб-сервер на Python с HTML-страницей: проще, но пользователь просил Tauri, и окно без вкладки браузера удобнее.

### Граница Rust / фронтенд

Вся работа с файлами и процессами в Rust-командах, фронтенд получает готовый JSON. Плагины `fs` и `shell` не подключаются, capabilities по умолчанию. Команды:

| Команда | Возвращает |
|---|---|
| `list_days()` | `[{day, active_minutes, work_minutes, has_report}]`, новые сверху |
| `get_day(day)` | `{day, active_minutes, unclassified, minutes: [{t, app, activity \| null, category \| null}], report: {generated_at, intervals: [{start, end, activity, category \| null}], stale} \| null}` |
| `classify_day(day)` | запускает доразметку, результат приходит событием `classify-finished` |
| `collector_status()` | `{running, pid \| null}` |
| `start_collector()` | `collector_status` после запуска или ошибку `{kind: "permission" \| "failed", message}` |
| `stop_collector()` | `collector_status` после остановки или ошибку |
| `open_screen_recording_settings()` | открывает раздел Screen Recording в System Settings |
| `generate_report(day)` | запускает сборку, результат приходит событием |

`get_day.minutes` — объединение `captures.jsonl` и `minutes.jsonl` по `t`, отсортированное по времени. `app` берётся из `minutes.jsonl`, если минута описана, иначе из `captures.jsonl`. `activity = null` означает «ещё не описано». Дубли по `t` — побеждает последняя строка. Битые строки JSONL пропускаются (последняя строка может быть записана наполовину).

`category` у минуты и интервала — `work`, `nonwork`, `idle` или `null`: поля нет (строка записана до появления категорий), значение неизвестное или минута ещё не описана. `work_minutes` — число минут дня с категорией `work`; `active_minutes` по-прежнему считается по `captures.jsonl`. `unclassified` — число описанных минут без категории, кроме `(нет описания)`: то же правило, по которому `classify` выбирает минуты.

`day` во всех командах проверяется по `^\d{4}-\d{2}-\d{2}$` до обращения к диску.

Каталог данных: `DAYLOG_DIR`, иначе `~/.local/share/daylog`. Каталоги дней — только те, чьё имя проходит ту же проверку.

### Обновление открытого дня

Фронтенд раз в 15 секунд перезапрашивает `get_day` для открытого дня, `list_days` и `collector_status`, только пока окно видимо (`document.visibilityState`). Данные дня — сотни строк, чтение дешёвое.

Альтернатива — крейт `notify` и события из Rust: точнее, но это лишняя зависимость и состояние ради обновления раз в минуту.

### `report.json`

`cmd_report` после получения интервалов пишет рядом с `report.md`:

```json
{"day": "2026-11-16", "generated_at": "2026-11-16T15:02:11", "minutes_count": 205,
 "intervals": [{"start": "09:28", "end": "09:29", "activity": "…", "category": "work"}]}
```

`minutes_count` — число минут в `minutes.jsonl` на момент сборки. Отчёт устарел (`stale`), если сейчас описанных минут больше. Запись через временный файл и `os.replace`, чтобы приложение не прочитало половину.

Дни, где есть только `report.md` (16.11.2026), приложение считает днями без отчёта: его пересобирают кнопкой. Разбор markdown не делаем.

Журнал для LLM при сборке отчёта — строки «ЧЧ:ММ | категория | приложение | что делал». `REPORT_SYSTEM` дополняется правилом: интервал не смешивает категории; `REPORT_SCHEMA` — полем `category` у интервала (`work | nonwork | idle`). `report.md` не меняется: категория в нём не печатается.

### Категории минут

Три значения: `work` («рабочее»), `nonwork` («нерабочее»), `idle` («ничего не делал»). Нет значения — `null`, в интерфейсе «не размечено».

Категорию ставит тот же вызов `claude -p` в `cmd_summarize`, что описывает минуты по снимкам: в `DESCRIBE_SCHEMA` у минуты добавляется обязательное поле `category` (enum), а строка в `minutes.jsonl` получает его рядом с `activity`. Лишних вызовов нет, и метка появляется вместе с описанием, без сборки отчёта.

Правила в `DESCRIBE_SYSTEM`:

- рабочее — то, что относится к задачам по работе: код, ревью, тикеты, рабочие чаты, встречи, документы;
- `idle` — только при явном простое: экран блокировки, заставка, пустой рабочий стол. Неизменный экран — не простой: человек мог читать. При сомнении — занятие, `work` или `nonwork` по содержанию экрана;
- если в каталоге данных есть `work.md`, его текст подклеивается к системному промпту как описание работы пользователя (что рабочее, что личное). Файл читается при каждом вызове, его правка действует на следующие минуты.

Минуты, для которых LLM не вернул описание (`(нет описания)`), категорию не получают.

Альтернатива — категория у интервалов только при сборке отчёта: дешевле на один параметр схемы, но без отчёта итогов дня нет, а отчёт собирается не всегда.

### Доразметка

`daylog.py classify [день]` (`cmd_classify`) размечает описанные минуты без `category` (кроме `(нет описания)`) по тексту описаний:

1. Берёт `summarize.lock` дня с ожиданием, как `summarize --flush`. Сборщик дописывает `minutes.jsonl` только из `cmd_summarize` под этой же блокировкой; фоновый `summarize` при занятой блокировке выходит и подхватит свои минуты на следующем заходе. Поэтому между чтением и перезаписью файла новых строк не появится.
2. Если размечать нечего — выходит без вызова LLM.
3. Один текстовый вызов `claude -p` без инструментов: на входе строки «ЧЧ:ММ | приложение | что делал» и те же правила категорий (включая `work.md`), на выходе `[{t, category}]`.
4. Переписывает `minutes.jsonl`: те же строки в том же порядке, у совпавших по `t` описанных строк без категории добавлено поле `category`; строки, которые не разбираются как JSON, сохраняются как есть. Запись через временный файл и `os.replace`. Ошибка LLM — файл не трогается, код выхода ненулевой.

`cmd_report` вызывает `cmd_classify` после `cmd_summarize(flush=True)` и до сборки интервалов.

В приложении доразметка запускается сама: фронтенд, получив `get_day` открытого дня с `unclassified > 0`, вызывает `classify_day(day)`. Rust запускает `daylog.py classify <день>` так же, как отчёт: в отдельном потоке, с множеством «дни в доразметке» под мьютексом, и шлёт событие `classify-finished` с `{day, ok, error}`. Второе множество — «дни, для которых доразметка уже запускалась» за этот запуск приложения: повторный вызов для такого дня ничего не делает, поэтому ошибка или минуты, которые LLM пропустил, не приводят к вызову при каждом опросе. Пока идёт доразметка, строка «не размечено» в итогах показывает «размечаю…»; ошибка показывается полосой, как ошибка отчёта. Отдельной кнопки нет.

Отвергнутые варианты: кнопка «Разметить» (лишнее действие) и доразметка только через отчёт (без отчёта у старых дней нет итогов).

Альтернатива — отдельный `categories.jsonl` рядом с `minutes.jsonl` без перезаписи: безопаснее для исходного файла, но два источника категории и правило их слияния в приложении. Перезапись под блокировкой и через `os.replace` достаточно надёжна.

### Запуск сборки отчёта

Rust запускает `python3 <daylog.py> report <day>` через `std::process::Command` в отдельном потоке (`tauri::async_runtime::spawn_blocking`), stdout/stderr захватывает. По завершении шлёт событие `report-finished` с `{day, ok, error}`; `error` — последние ~500 символов stderr. Состояние «для этого дня уже идёт сборка» хранится в `tauri::State` (множество дней под мьютексом); повторный вызов для того же дня возвращает ошибку «уже собирается».

Поиск исполняемых файлов. У приложения, запущенного из Finder, PATH урезан:

- `python3`: первый существующий из `DAYLOG_PYTHON`, `/opt/homebrew/bin/python3`, `/usr/local/bin/python3`, `/usr/bin/python3`.
- `daylog.py`: `DAYLOG_SCRIPT`, иначе путь, зашитый при сборке: `concat!(env!("CARGO_MANIFEST_DIR"), "/../../daylog.py")`. Приложение собирается из этого же репозитория, поэтому путь верный.
- `claude` ищет сам `daylog.py` (уже есть запасной путь `~/.local/bin/claude`). Дочернему процессу в PATH добавляются `~/.local/bin` и `/opt/homebrew/bin`.

Таймаута на стороне Rust нет: `daylog.py` сам ограничивает каждый вызов LLM 300 секундами, но `report` перед сборкой дописывает неописанные минуты, и их может быть много.

### Блокировка сборщика и его состояние

`cmd_run` в начале открывает `$DAYLOG_DIR/collector.lock` (режим `a+`, без усечения), берёт `fcntl.flock(LOCK_EX | LOCK_NB)`, после этого перезаписывает файл своим PID и держит его открытым до выхода. Если блокировка занята — повторяет попытки в течение 1 секунды (приложение могло занять её на мгновение для проверки), затем выходит с кодом 2 и сообщением «сборщик уже запущен (PID N)». Файл не удаляется.

Состояние определяется блокировкой, а не PID: Rust открывает файл и пробует `libc::flock(LOCK_EX | LOCK_NB)`. Получилось — сборщика нет, блокировку сразу отпускаем. `EWOULDBLOCK` — сборщик работает, PID читаем из файла. Так не мешают устаревший PID после падения, переиспользование PID и зомби-процесс.

Альтернативы: `kill(pid, 0)` по PID из файла (врёт при зомби и переиспользовании PID); поиск `daylog.py run` в списке процессов (зависит от формы командной строки).

### Запуск и остановка сборщика

Источник правды — блокировка, поэтому приложение одинаково работает со сборщиком, запущенным им самим, оставшимся от прошлого запуска приложения и запущенным из терминала.

Запуск (`start_collector`):

1. Если блокировка занята — вернуть текущее состояние, ничего не запускать.
2. Проверить разрешение: `CGPreflightScreenCaptureAccess()`. Если его нет — вызвать `CGRequestScreenCaptureAccess()` (система покажет запрос и добавит приложение в список) и вернуть ошибку `permission`. macOS применяет выданное разрешение после перезапуска приложения; об этом сказать в тексте ошибки.
3. Запустить `python3 <daylog.py> run` тем же способом поиска путей, что и для отчёта. stdin — `/dev/null`, stdout и stderr дописываются в `$DAYLOG_DIR/collector.log`. Процесс — в собственной группе (`process_group(0)`), чтобы его не задевали сигналы приложения.
4. Ждать до 3 секунд: блокировка занята — успех. Процесс завершился — ошибка: код 3 → `permission`, иначе `failed` с последними ~500 символами `collector.log`.

`Child` хранится в `tauri::State`; при опросе состояния вызывается `try_wait`, чтобы не копить зомби.

Чтобы отличать отсутствие разрешения, `cmd_run` при неудачном пробном кадре выходит с кодом 3 (сейчас `sys.exit(строка)` даёт код 1). Текст сообщения заменить на нейтральный: разрешение нужно приложению или терминалу, из которого запущен сборщик.

Остановка (`stop_collector`): PID из `collector.lock`, при занятой блокировке — `SIGTERM`, затем до 5 секунд ждать освобождения блокировки. Не освободилась — ошибка, без `SIGKILL`. Сигнал отправляется только при занятой блокировке, поэтому чужой процесс с переиспользованным PID не пострадает. Фоновый `summarize`, если он в этот момент работает, доживает сам. В `cmd_run` обработчик `SIGTERM` не нужен: поведения по умолчанию достаточно.

Окно и выход:

- Закрытие окна перехватывается (`CloseRequested` → `prevent_close` + `hide`); приложение остаётся в Dock, событие `Reopen` показывает окно.
- При выходе (`RunEvent::ExitRequested`) приложение останавливает сборщик, только если запустило его само в этом сеансе. Сборщик из терминала не трогает.

Возобновление: в каталоге конфигурации приложения (`app_config_dir`) файл `state.json` с `{"recording": bool}`. Кнопка запуска пишет `true`, кнопка остановки — `false`, выход из приложения значение не меняет. При старте приложения при `recording: true` и свободной блокировке вызывается тот же `start_collector`; ошибка показывается так же, как при нажатии кнопки.

Альтернатива — отвязанный сборщик, переживающий выход из приложения: запись без Dock-иконки незаметна и остановить её можно только из приложения или `kill`; отказались.

Разрешение в режиме разработки: при `pnpm tauri dev` бинарник запущен из терминала, разрешение берётся у терминала. У собранного `.app` — своё.

### Экран

Одно окно, минимум 900×600.

- Слева список дней: дата с днём недели, рабочее время и время за компьютером (`работа 2 ч 10 мин из 3 ч 25 мин`), точка, если отчёт собран. Сверху сегодняшний день; он открыт при старте.
- Шапка: дата, рабочее время, время за компьютером, первая и последняя минута (`работа 2 ч 10 мин · за компьютером 3 ч 25 мин · 09:28–15:57`), кнопка «Собрать отчёт» / «Пересобрать отчёт». Справа в шапке, независимо от открытого дня, — кнопка записи: ▶ «Начать запись» / ■ «Остановить» и индикатор (красная точка «запись идёт» / серая «запись не идёт»). Пока запрос запуска или остановки выполняется, кнопка недоступна. Ошибка запуска показывается полосой под шапкой; для `permission` в ней кнопка «Открыть настройки» и текст «после выдачи разрешения перезапустите daylog».
- Полоса дня: горизонтальная шкала от часа первой минуты до часа после последней, по сегменту на минуту, цвет по категории, описанные минуты без категории — нейтральным серым, неописанные полупрозрачные, пропуски пустые. Наведение — подсказка «ЧЧ:ММ · категория · приложение · что делал». Клик — открывает вкладку «Минуты» и прокручивает к этой минуте.
- Вкладка «Таймлайн»: интервалы из `report.json` (`09:29–09:33`, длительность, цветная метка категории, текст). Если отчёт устарел — строка «есть новые минуты после сборки». Если отчёта нет — пустое состояние с той же кнопкой.
- Вкладка «Минуты»: все минуты дня, строка = время, метка категории (цветная точка), приложение, описание; неописанные — «ещё не описано» серым, описанные без категории — с пометкой «не размечено». Поле поиска фильтрует по подстроке без учёта регистра в приложении и описании. Пропуск от 5 минут между соседними строками показывается разделителем «не за компьютером 12 мин» (только без активного поиска).
- Справа «Итоги дня»: «Рабочее», «Нерабочее», «Ничего не делал» и «Не размечено» (если такие минуты есть) в этом порядке — минуты и доля от времени за компьютером. Клик по категории фильтрует вкладку «Минуты», повторный клик снимает фильтр. Разбивки по приложениям нет; приложение остаётся в строке журнала и в подсказке.

Цвета категорий фиксированные, со своими оттенками для светлой и тёмной темы: рабочее — зелёный, нерабочее — оранжевый, ничего не делал — серо-синий, не размечено — нейтральный серый. Цвет приложения из хеша имени больше не нужен.

Время за компьютером дня = число уникальных минут в `captures.jsonl`.

### Тесты

- Rust: модульные тесты разбора каталога дня на временных каталогах (`tempfile`): объединение captures/minutes, сортировка, дубли, битая строка, день без `minutes.jsonl`, признак `stale`, отбрасывание некорректного имени дня, разбор `category` (нет поля и неизвестное значение → `null`), `work_minutes`. Состояние сборщика: свободная и занятая блокировка. Запуск и остановка — с подставным скриптом через `DAYLOG_SCRIPT` (держит блокировку и спит; выходит с кодом 3; выходит с кодом 1), проверку разрешения в тестах обходить параметром функции.
- Фронтенд: чистые функции (форматирование длительности, пропуски, фильтр по подстроке и категории, итоги по категориям) в отдельном модуле, тесты на vitest. Компоненты тестами не покрываем.
- `daylog.py`: без тестового каркаса, проверка руками командами из tasks.md. `summarize` и `classify` — через `python3 -c` с подменой `ask_claude` на копии дня; один настоящий вызов `classify` и `report` на копии.

## Risks / Trade-offs

- [Сборка отчёта из приложения, запущенного из Finder, не находит `claude` или `python3`] → явный список путей и добавка к PATH; ошибка с хвостом stderr показывается в окне; переопределение через `DAYLOG_PYTHON` и `DAYLOG_SCRIPT`.
- [Путь к `daylog.py` зашит при сборке; после переноса репозитория сборка отчёта сломается] → пересобрать приложение или задать `DAYLOG_SCRIPT`.
- [`report` перед сборкой дописывает все неописанные минуты; для дня с большим хвостом это долго и стоит денег] → кнопка блокируется на время сборки и показывает «собираю…»; поведение то же, что из терминала.
- [Отчёт пересобирается целиком при каждом нажатии] → принято; день — это сотни строк текста.
- [Опрос раз в 15 секунд вместо слежения за файлами] → задержка до 15 секунд при минутной частоте записи несущественна.
- [Работающий сейчас сборщик запущен старой версией и блокировку не держит: приложение покажет «запись не идёт» и запустит второй] → перед первым запуском записи из приложения остановить сборщик в терминале; шаг есть в tasks.md.
- [Собранный локально `.app` подписан ad-hoc, и после пересборки macOS может считать его другим приложением: разрешение Screen Recording придётся выдать заново] → пересобирать редко; ошибка `permission` ведёт в настройки. Если начнёт мешать — подписывать постоянным самоподписанным сертификатом (`bundle.macOS.signingIdentity`).
- [Без разрешения `screencapture` на части версий macOS не падает, а снимает только обои] → проверка разрешения через `CGPreflightScreenCaptureAccess` до запуска сборщика, а не только по пробному кадру.
- [Cmd+Q по привычке останавливает запись] → закрытие окна запись не трогает, при следующем запуске приложения запись возобновляется сама.
- [Сборщик аварийно завершился посреди дня, а окно скрыто] → пользователь узнает, только открыв окно. Принято для первой версии; лечится иконкой в строке меню.
- [Последние до 4 минут перед остановкой остаются неописанными] → как и сейчас, их дописывает сборка отчёта; в журнале они видны как «ещё не описано».
- [LLM ошибается с категорией: личный разговор в рабочем Slack, свой проект в рабочем терминале] → описание работы в `work.md`; ошибки видны в журнале, правка `work.md` действует на следующие минуты.
- [Перекос в сторону «занят»: часть простоя попадёт в рабочее или нерабочее] → принято сознательно: ложное «ничего не делал» хуже, чем недосчитанный простой.
- [`classify` перезаписывает `minutes.jsonl` — основной файл данных] → под `summarize.lock`, через временный файл и `os.replace`, неразборчивые строки сохраняются как есть; ошибка LLM файл не трогает.
- [Доразметка старых дней стоит денег, а листание дней запускает её само] → один текстовый вызов на день, не больше одного за запуск приложения; размеченный день повторно не размечается.

## Migration Plan

1. Правки `daylog.py` обратно совместимы по данным и по запуску из терминала. Новые минуты размечаются сразу после обновления файла: сборщик запускает `summarize` из `daylog.py` на диске, перезапуск не нужен. Минуты, описанные раньше, размечаются сами при открытии дня в приложении (или `daylog.py classify <день>`).
2. Собрать приложение: `cd app && pnpm install && pnpm tauri build`, положить `.app` в `/Applications`.
3. Остановить сборщик во вкладке терминала (Ctrl+C), запустить daylog.app, нажать «Начать запись», выдать разрешение Screen Recording, перезапустить приложение.
4. Откат: запускать `daylog.py run` в терминале, как раньше; удалить `app/`. `report.json`, `collector.lock`, `collector.log` ничему не мешают.
